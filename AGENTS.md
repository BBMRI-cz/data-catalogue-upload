# AGENTS.md

Guidance for AI coding agents (primarily Claude Code) working in this repository. `CLAUDE.md` mirrors this file for Claude Code discovery. Project-specific skills live in `.claude/skills/`.

## Project

`data-catalogue-upload` is a **.NET solution** for the data-catalogue sync system. The solution is `DataCatalogueUpload.slnx` at the repo root. The services:

- **uploader** (`src/Uploader`) - a long-running sync service that syncs on an in-process Quartz schedule and on demand. For each patient it reads from four source APIs (biobank, radiology, sequencing, WSI), aggregates the data into one FAIR Genomes-shaped patient record, compares it against fingerprints stored in PostgreSQL, and saves/deletes rows in a **MOLGENIS EMX2** catalogue over GraphQL. The contract, verified against the live instance, is [`docs/catalogue-api-contract.md`](docs/catalogue-api-contract.md) - read it before touching the gateway.
- **biobank_api** (`src/BiobankApi`) - a source API service that parses biobank XML exports and serves the patient/sample/clinical endpoints the uploader consumes.
- **sequencing_api** (`src/SequencingApi`) - source API service for sequencing data. Domain (#54), persistence (#55) and MMCI ingestion (#56/#57) have landed. Same layering and in-process Quartz ingestion as biobank_api.
- **TrainingSeeder** (`tools/TrainingSeeder`) - not a service: a one-shot tool that fills an empty biobank_api and sequencing_api database with a synthetic training dataset for work off our servers (#112). It draws every value from the real value counts exported by its read-only `export-vocabulary.sql` (the two `*-vocabulary.json` files, embedded at build) and generates every identifier and date. It builds aggregates through the domain `Create(...)` factories and saves them through the services' own repositories - composed per database by each service's `AddInfrastructure`, under a `BIOBANK_`/`SEQUENCING_` prefix on `POSTGRES_*` - so a schema change reaches it without edits. It only fills **empty** databases and only migrates one with no schema yet, because the repositories delete-then-insert on ids that could be real ones. Run only by `compose.training.yml`; no service references it. [`docs/training-dataset.md`](docs/training-dataset.md) is its guide.

Read [`ARCHITECTURE.md`](ARCHITECTURE.md) for the data flow and layering, and [`DEVELOPMENT.md`](DEVELOPMENT.md) for setup and local run instructions.

## Solution layout

- **.NET 10** (`net10.0`), pinned via `global.json`. Nullable + implicit usings on; warnings are errors (NuGet audit advisories `NU190x` are warnings only).
- **One solution, central package management**: `Directory.Build.props` (shared TFM/analyzers) and `Directory.Packages.props` (all NuGet versions). Do not put `Version=` on individual `PackageReference`s.
- **No shared kernel** - each service owns its own DDD base types (small, deliberate duplication; zero cross-service coupling).

```
DataCatalogueUpload.slnx  Directory.Build.props  Directory.Packages.props  global.json
src/
├── BiobankApi/     BiobankApi.{Domain,Application,Infrastructure,Web}
├── SequencingApi/  SequencingApi.{Domain,Application,Infrastructure,Web}
└── Uploader/       Uploader.{Domain,Application,Infrastructure,Host}
tools/

tests/

├── Uploader.{UnitTests,IntegrationTests}
└── TrainingSeeder.IntegrationTests
```

Dependency direction per service: `Web`/`Host` -> `Infrastructure` -> `Application` -> `Domain`.

## Architecture (both services)

- **Clean Architecture + DDD.** Domain holds aggregates (`PatientAggregate` in biobank_api and the uploader; `SampleAggregate`/`SequencingRunAggregate`/`PanelAggregate` in sequencing_api), value objects, and invariants. The uploader adds the domain service `ISyncPlanner` (`FingerprintSyncPlanner`); change detection compares a `Fingerprint.Of(...)` of the catalogue row the handler would send - the rules live in the domain planner, the row is built in Application, and hashing the row rather than the aggregate is what re-sends a mapping fix. The uploader's patient, sample and sequencing aggregates hold only what the planner reads (identity, consent, links); their rows are built straight from the biobank and sequencing responses. The biobank has no domain service - XML text cleaning lives in infrastructure (`XmlValueReader`). Domain has no I/O and no framework dependencies.
- **CQRS via Mediator.** Every use case is a `Command`/`Query` with a handler in `*.Application/Features/...`, dispatched through the free `Mediator` source generator (`ISender`). Handlers return `ErrorOr<T>`. A non-trivial result type is named after its request - `<Command>Result` (e.g. `RunCatalogueSyncCommandResult`, `IngestExportsCommandResult`) - in the same `Features/` folder.
- **Pipeline behaviors** (`*.Application/Behaviors`): `LoggingBehavior` wraps each request; `ValidationBehavior` runs any FluentValidation `AbstractValidator<TCommand>` (auto-registered via `AddValidatorsFromAssembly`) and short-circuits to an `ErrorOr` validation error before the handler. Application-level request validation lives here; domain invariants stay in the aggregate `Create(...)` factories. (Current commands are parameterless, so no validators exist yet.)
- **Ports are interfaces** in `*.Application/Abstractions`, implemented in `*.Infrastructure` (EF Core repositories, the biobank XML parser, the uploader's typed `HttpClient` gateways).
- **One aggregate root = one repository, named after the root** - not after the service: port `I<Root>Repository`, EF implementation `Sql<Root>Repository`, test fake `Fake<Root>Repository`. A port that projects *across* aggregates into flat DTOs is a **`I<Thing>Reader`**, never a `Repository` - a repository returns aggregates through the mappers, a reader projects in SQL and never round-trips the domain. **Run logs are the one exception:** `sync_run` and `ingest_run` record what a run did rather than a domain concept, so they have no aggregate; their port (`ISyncRunRepository`, `IIngestRunRepository`) writes the row and reads back a flat record (`SyncRun`, `IngestRun`), and keeps the `Repository` name. Saves are idempotent delete-then-insert on the natural id and report per-record failures instead of aborting; aggregate roots reference each other **by id, with an index but no foreign key**, so ingest order never becomes load-bearing.
- **Don't flatten value objects into their owner's row.** A 0..1 value object gets its own table keyed on the owner's primary key - that is what makes it one-to-one, and absence becomes an absent row instead of a nullable column group needing a marker to tell "not recorded" from "recorded, all fields unknown". An ordered child collection gets rows with an explicit position column. JSON columns are only for **scalar** lists (`patient.AccessionNumbers`, `panel.Genes`), plus a run log's error list (`ingest_run.Errors`), which is written once and only ever read back whole.
- **API style:** ASP.NET Core Minimal API; endpoints only build a Command/Query and call `ISender`, then map `ErrorOr` to HTTP via `ErrorResults`. Work that must outlive the request - a sync, an ingest - goes to the host's runner instead (`SyncRunner`, `IngestionRunner`), which sends the command itself; that endpoint answers `202` when the run starts, `409` when one is already running.

## biobank_api

EF Core (Npgsql) + LINQ-to-XML (`System.Xml.Linq`). Domain `PatientAggregate` with `TissueSample`/`SerumSample`/`GenomeSample` and `DiagnosticSpecimen`; invariants enforced by `Create(...)` factories returning `ErrorOr`. Ingestion reads exports behind the `IPatientExportSource` port (`XmlExportParser` discovers files, the pure `XmlPatientReader` maps each `<patient>`). **A patient recurs in every weekly file, but each file lists only the last ~60 days of samples and specimens**, so `PatientExportHistory` merges all of a patient's files instead of letting the newest win: the header (consent, sex, birth date, patient accession numbers) comes from the newest file, samples accumulate keyed on type + `sampleId` (a newer listing replaces all of that sample's older rows), specimens accumulate keyed on `sampleId`, and a newest `consent="false"` clears them all. The API's data therefore depends on the whole export archive - never prune it. There is exactly one source per biobank, and the handler reads it and reports invalid records in an `IngestExportsCommandResult`. The Application ports live in subfolders: `Abstractions/Export/` (`IPatientExportSource`, `ExportParseResult`, `ExportParseError`) and `Abstractions/Repositories/` (`IPatientRepository`, implemented by `SqlPatientRepository`). CQRS: `GetPatientsQuery`, `IngestExportsCommand`. Host `BiobankApi.Web` runs the Minimal API and a **weekly Quartz job** (`IngestionJob`); it and `POST /admin/ingest` both start `IngestExportsCommand` through the singleton `IngestionRunner`, so a manual and a scheduled ingest never overlap. `POST` answers `202` at once (`409` while one runs); `GET /admin/ingest` reports `{running, last_run}` from the `ingest_run` table, which the handler writes as the ingest starts and completes with the counts, the per-record errors (a JSON text column) or the `failure` reason. Config via env vars (`POSTGRES_*`, `BIOBANK_*` incl. `BIOBANK_INGEST_CRON` for the schedule); see `BiobankOptions`.

## sequencing_api

Mirrors biobank_api (host + ingestion handler persisting through the repositories). Domain is a biobank-agnostic sequencing model derived from [`docs/sequencing-data-report.md`](docs/sequencing-data-report.md) §4, with **three aggregate roots**: `SampleAggregate` (`Samples/`, keyed by an opaque `external_id` + `IdScheme`, owning `RunSample` -> `LibraryPreparation`/`SequencingFile`/`Analysis`), `SequencingRunAggregate` (`Runs/`, + `ReadDefinition`) and `PanelAggregate` (`Panels/`). Runs and panels are shared by many samples, so they are referenced by id, never embedded. `QualityMetrics` and the enums (`SampleType`, `FileRole`, `AnalysisType`) sit at the Domain root. **Individual variant records are deliberately not modelled** - the catalogue consumes none of them; analyses reference their calls as files (`FileRole.Vcf`/`VariantReport`). **`QualityMetrics` holds only the two numbers the catalogue consumes** (`MedianReadDepth`, `ObservedReadLength`) - FAIR Genomes names six quality fields and MMCI's sources state only these two; the same rule that keeps variants out keeps the rest out. **It attaches to `Analysis` only** - both are computed by the pipeline, so the run carries a plain `PercentageQ30` instead and `RunSample` carries no quality at all. Invariants **and value cleaning** live in the `Create(...)` factories via the internal `Common/Normalize` helper (trim/collapse/case-fold/symbol lists); source decoding - text encoding, decimal commas, panel alias matching - stays in Infrastructure. Ingestion reads the `ISequencingDataSource` port (`Abstractions/DataSource/`), implemented per facility under **`Infrastructure/DataSource/<Facility>/` - one directory per source adapter** (`DataSource/Mmci/` is the first): the tree walk plus readers for the run metadata XML, sample sheet, sample folders, NextGENe statistics, the versioned libraries table and the pseudonymizer's `predictive.json`. That mapping file is the only route from the pseudonymized predictive number (the sample folder name, which becomes `SampleAggregate.Id`) to the real one (`SampleAggregate.PredictiveNumber`, the key biobank_api stores as `predictive_number` - the report calls this field `subject_ref`, but it is a predictive number and is named one); the `patient.json`/`samples.json` beside it are never opened. **[`docs/mmci-ingestion-map.md`](docs/mmci-ingestion-map.md) maps every domain field to the exact source file, key and reader that fills it - read it before changing a reader or chasing an empty field.** Missing libraries or mapping tables are reported, not fatal - they cost panels and predictive numbers respectively, not the sequencing data. **Persistence** is nine tables - `sample`, `run_sample`, `library_preparation`, `analysis`, `quality_metrics`, `sequencing_file`, `sequencing_run`, `run_read`, `panel` - behind one repository per aggregate root (`ISampleRepository`, `ISequencingRunRepository`, `IPanelRepository`) plus the cross-aggregate `ISequencingStatsReader`. **Value objects are never flattened into their owner's row:** the 0..1 `LibraryPreparation` and `QualityMetrics` each own a table keyed on the owner's primary key (which is what makes them one-to-one and lets an absent value object simply be an absent row), and a run's ordered read structure is `run_read` rows with an explicit `Position`, not a JSON blob. Only `panel.Genes` is a JSON column, because it is a scalar string list - the same treatment `patient.AccessionNumbers` gets. Sequencing and analysis outputs do share the `sequencing_file` table, told apart by which owner FK is set, with a check constraint enforcing exactly one. Host `SequencingApi.Web` runs the Minimal API (`GET /health`, `GET /sequencing?predictive_number=`, `GET /summary`, `POST`/`GET /admin/ingest`) and a **weekly Quartz job** (`IngestionJob`), both starting the ingest through `IngestionRunner` exactly as biobank_api does, with its own `ingest_run` table. `GET /sequencing` takes the **real** predictive number and matches it on its canonical `year-number` key (`SampleAggregate.PredictiveKey`, derived by `Normalize.PredictiveKey` and stored indexed), so the biobank's `2029/5678` finds a sample sheet's `2029_5678_DNA` or `5678-29` - a number with no recognisable form has to match exactly; it serves this service's own model (the uploader maps it to FAIR on its side, as with biobank_api), and answers an unknown number with `200` + empty `samples` rather than `404` - the uploader's gateway calls `EnsureSuccessStatusCode`, so a 404 would throw there; a *missing* parameter is a `400`, via the `GetSequencingQueryValidator`. Config via env vars (`POSTGRES_*`, `SEQUENCING_*` incl. `SEQUENCING_INGEST_CRON`); see `SequencingOptions`. Search for `ponytail:` to find the remaining spots to fill in.

## uploader

EF Core (Npgsql) + typed `HttpClient`s. Domain: `PatientAggregate` (id, consent), `SampleAggregate` (id, patient id, sequencing and WSI ids) and `SequencingAggregate` (predictive number, owning sample id) hold only what the planner reads - no copy of the catalogue row - beside the WSI/radiology aggregates with their value objects and the `*SyncState` types; `FingerprintSyncPlanner` decides CREATE/UPDATE/SKIP/DELETE. CQRS: `RunCatalogueSyncCommand`. **Each source API serves its own vocabulary and the uploader translates** - mappers in `Application/Mapping/`, over DTOs in `Application/Dtos/` whose property names mirror the source's response records (both sides use `SnakeCaseLower`, so matching names are what makes the wire keys line up; `BiobankContractParityTests` and `SequencingContractParityTests` guard that, each against a recorded response under `tests/Uploader.IntegrationTests/TestData/`). The biobank's and sequencing API's responses are mapped **straight to their catalogue payloads** by `CataloguePatientMapper`, `CatalogueSampleMapper` and `CatalogueSequencingMapper`, which also build the thin aggregates; WSI and radiology still map to an aggregate first. The biobank's `p_tnm`, `morphology`, counts and the rest have no catalogue column yet and are dropped deliberately - each mapper names what it drops and why. **An ontology value is resolved before its row is fingerprinted**, so a mapping that starts answering re-sends the row: the patient's fields (`Personal.genderAtBirth`, `Personal.primaryAffiliatedInstitute`, `Clinical.diagnosis`), the sample's (the four material-code columns `Material.materialType`/`pathologicalState` and `Biospecimens.biospecimenForm`/`storageConditions`, plus `Biospecimens.managingBiobank` and `availability`) and the sequencing's (`SamplePreparation`'s two kits and two gene lists, `Sequencing.sequencingPlatform`/`sequencingInstrumentModel`/`sequencingMethod`, `Analysis.dataFormatsStored`/`referenceGenomeUsed`) go to the run's `TermResolver` exactly as the source served them (`female`, `MOU`, `C504`, `53`, `BRCA1*`, `NB552710`, `vcf_filtered`, `hg19`), which uses a value that is already a live term as is, otherwise asks the `IMappingTable` port (a term - used only if live -, "no term", or not found), and otherwise leaves the field out of a row that still goes out and records the value as unmapped. `RuleMappingTable` stands in for the ontology-mapping student's approved table until it exists, handing every run `RuleMappingSnapshot`, which holds today's rules (sex, institute, ICD-10 dot rule, material codes, gene star, platform, instrument-serial prefix, file role, reference-genome alias; kits have no rule and publish only as a live term); switching is a swap of that one registration. A run reads the live term list of all 18 fields in `OntologyFields` (`ICatalogueGateway.ReadTermListsAsync`) and loads the mapping table after the study upsert, and ends before the first patient, with a `failure`, when either cannot be had - a save replaces the whole row, so resolving against a missing list would erase published terms. **A material code is looked up with its context** - the sample type and the biobank API's `material_type_label` (`TermContext.Material`) - because one code means a different material per sample type; the lookup key is field, value and whole context. The stand-in answers "no term" for the documented deliberate empties (benign and premalignant tissue, mononuclear cells, primary cell cultures, RNAlater storage, a blood draw's pathological state) and not found for anything no rule has decided, so a new material code or biobank code is reported rather than lost. Availability (`Depleted` at zero units left, `Available` otherwise, in `CatalogueSampleMapper`) and the sequencing method (the constant `Illumina Sequencing`, in `SequencingMapping`) are computed, not mapped, but still pass the live-term check. **The gene star is placement**: `CatalogueSequencingMapper` reads it only to put a starred symbol in `fullySequencedGenes` and the rest in `partiallySequencedGenes`; the symbol reaches the resolver with its star, and the stand-in takes it off. Unmapped values are kept only for upload-eligible patients and logged once per distinct value per run, with their context. A rule only maps a value when a term genuinely means the same thing - EMX2 enforces ontology columns as foreign keys, so an invented term fails the whole row. [`docs/ontology-mapping.md`](docs/ontology-mapping.md) covers the resolver, the three answers, the stand-in and the switch. **Sequencing is the one source whose response is a nested list**: `samples[] -> runs[]`, flattened into one `SamplePreparationRecord` per pair on `CatalogueSequencingPayload.SamplePreparations`, so a resequenced sample loses nothing; an unknown predictive number answers `200` with an empty `samples`, which yields no aggregate and no failure (`CatalogueSequencingMapper.HasPreparations` is false). **MammaPrint runs are left out by the uploader**, not the sequencing API, which serves every run: `CatalogueSequencingMapper` drops a run filed under `mamma-print` or named `MP_*` (the API serves `source_class` and `experiment_name` for this), and a number with nothing else yields no aggregate, so its published rows are deleted. **A predictive number belongs to a case, not to a sample** - every sample of one surgery carries it - so the handler fetches each number once and builds one `SequencingAggregate` owned by the sample `SequencingOwner` picks (malignant tumour tissue, then metastasis, their RNAlater forms, other tissue, serum, genome; ties by collection, then sample id). Built per sample, the copies shared one sync record, moved each other's `belongsToBiospecimen` on every run, and a delete looked under whichever sample the record named last - which is how 105 MammaPrint rows survived their delete. `save` never removes rows, so `UpsertSequencingAsync` reads the owner's published sequencing subtree after saving and deletes the rows it did not send - which is what removes a dropped run from a number that still has others. Its drops are the run-sample's `files` (FAIR Genomes has no file inventory, and v2 removed even the data-location columns v1 had, so an analysis output survives only as its `DataFormatsStored`), every panel field but `genes`, and `sample_type`/`analysis_type`/`id_scheme`/`sample_index`/`instrument_model` (the model is resolved from `instrument_id`, by the stand-in's serial-prefix rule)/`assay`/`workflow`; the run statistics FAIR does not name (cluster counts, density, yield, flowcell, completion status) are packed into `OtherQualityMetrics` by `SequencingMapping`, which also derives the FAIR identifiers. A patient is uploaded only when `PatientCatalogueData.IsUploadEligible`: consented **and** carrying at least one sample. **A source that is absent must not cost the run**: `ISourceDataGateway` returns `ErrorOr<T>` and never throws, a source whose URL is blank is not deployed and is never contacted at all (radiology and WSI default to blank), and the summary counts an unreachable service (`SourceUnavailable`) apart from an unreadable payload (`Failed`). Host `Uploader.Host` is a Minimal API like the source APIs (`GET /health`, `POST /admin/sync`, `GET /admin/sync`, port 8003, loopback only) with a Quartz `SyncJob` on `UPLOADER_SYNC_CRON` (default `0 0 2 ? * MON,WED,FRI`, UTC). **Both triggers go through the singleton `SyncRunner`**, whose one-slot lock means a sync never runs twice at once: `POST` starts one in the background and answers `202`, or `409` while one runs, and a scheduled turn that finds one running is skipped rather than queued. The handler records the run in `sync_run` **as it starts** (`ISyncRunRepository.StartAsync`) and completes the row at the end with the counts and, for a run that stopped before syncing anything, a `failure` reason; a row left without `finished_at` while nothing runs is a run cut short. `GET /admin/sync` answers `{running, last_run}` from that table, so a failed run is visible without watching the process. **Identifiers are pseudonymized on the way out**, by the mappers that build the EMX2 rows in `Application/Dtos/Catalogue/` that `ICatalogueGateway` writes - `CataloguePatientMapper` and `CatalogueSampleMapper` from the biobank response, `CatalogueSequencingMapper` from the sequencing response - so aggregates and sync state keep the real ids, payloads carry pseudonyms, and the type says which side a value is on. The handler builds each patient, sample and sequencing payload **once per run**, after resolving that patient's pseudonyms (sequencing under its owner sample's); the planner's fingerprint hashes that object and the upsert sends the same one. Only the patient and sample ids are minted (`IPseudonymMap`/`PseudonymStore`, the `pseudonym` table, prefix `PSEUDONYM_PREFIX`): the clinical, consent and biospecimen identifiers all derive from one of those two via `BiobankMapping`, and the whole sequencing chain is already pseudonymous because `SequencingMapping` derives it from the sequencing API's `sample_id`, which is the run tree's `mmci_predictive_<uuid>` folder name. **The pseudonymizer's mapping files are never read.** WSI and imaging-study upserts return `Catalogue.NotPseudonymized` rather than publishing real bioptic/accession numbers, since no source fills them yet. `CataloguePayloadLeakTests` is the guard; [`docs/pseudonymization.md`](docs/pseudonymization.md) shows the mapping per catalogue table. **One aggregate is several EMX2 rows**, so `ICatalogueGateway` has a method per aggregate rather than per table and owns the write order (patient = `Personal` -> `IndividualConsent` -> `Clinical`); deletes run that backwards, child before parent, because EMX2 refuses to delete a row another row still references - which is what stops a removed patient leaving orphaned samples behind. **A row is deleted only when its source said it was gone**: an aggregate missing because a source did not answer is not an aggregate that was withdrawn, so `PatientCatalogueData.SequencingComplete` and its siblings tell `FingerprintSyncPlanner` which sources reported and it leaves the rest alone - otherwise a network blip deletes published data. A patient who stops being `IsUploadEligible` (consent withdrawn, last sample gone) is **deleted rather than skipped** if it was ever published (`ISyncState.WasPublished`: a catalogue id, or an upsert that failed part-way), ordered last after their own children, and takes everything with them regardless of which sources answered; an ineligible patient who was never published gets no operation and leaves no sync state. An entity with no catalogue id is a CREATE whatever its stored fingerprint, and one whose last upload failed is sent again on the next run. `Emx2Schema` reads the live column layout and ontology terms once per run - the same read serves the resolver's term lists - wraps references into the nested key objects EMX2 wants, and, as a safety net, drops a term the ontology does not have rather than failing the row. Config via env vars (`POSTGRES_*`, `BIOBANK_API_URL`, `SEQUENCING_API_URL`, the blank-by-default `RADIOLOGY_API_URL`/`WSI_API_URL`, `CATALOGUE_API_URL`/`_SCHEMA`/`_TOKEN`/`_STUDY_ID`/`_STUDY_NAME`, `PSEUDONYM_PREFIX`; see `UploaderOptions`), plus `UPLOADER_SYNC_CRON` and `RUN_MIGRATIONS`, read by the host. **The catalogue token comes from `.env`, which is git-ignored** - copy `.env.example`.

**Deployment is three stacks, one compose file each**: `compose.biobank.yml`, `compose.sequencing.yml` and `compose.uploader.yml`. A fourth file, `compose.training.yml`, is not a deployment: both APIs over the seeder's synthetic data on tmpfs databases, kept out of the production files so no setting on a server can seed a real database. The two source stacks are pinned to a machine by what they read (`/home/mou/patient_data`, `/muni-sc/OrganisedRuns`) because a bind mount resolves only on the host running the container - point one at a path the host lacks and Docker makes an empty directory rather than failing. The uploader reads no files and goes anywhere; its `/admin/sync` writes to the real catalogue unauthenticated, so it is published on loopback only, with no bind variable. Run all three on one host and they are still three projects on three networks, so container names do not resolve between them and the uploader addresses sources as `host.docker.internal`. Ports bind to loopback by default: neither source API authenticates anything and `/patients` serves real identifiers. [`docs/deployment.md`](docs/deployment.md) is the runbook.

## Conventions

- **Respect layer boundaries.** Domain must not reference Application or Infrastructure. Application depends on Domain and its own port interfaces, never concrete infrastructure. Infrastructure implements the ports.
- **Domain models are `record`s** (value semantics); invariants live in `Create(...)` factories returning `ErrorOr` (throw `InvalidOperationException` only for unreachable/programmer-error guards). Mutable sync-state classes are the deliberate exception.
- **No primary constructors on classes or structs.** Use an explicit constructor that assigns `private readonly` fields (`_camelCase`). Positional **records** for DTOs/value objects/typed ids are fine - that idiom stays. (Enforced by `dotnet_diagnostic.IDE0290.severity = none` in `.editorconfig`.)
- **New external dependency?** Define an interface in `*.Application/Abstractions` and implement it in `*.Infrastructure`.
- **Handlers return `ErrorOr<T>`**; don't throw for expected failures. Validate domain invariants where the data becomes a domain object - the aggregate factory (`Create(...)`) returns an `ErrorOr` validation error; validate request shape/options at the application boundary with a FluentValidation `AbstractValidator<TCommand>` (the `ValidationBehavior` runs it) - and let the handler/endpoint propagate failures via `ErrorResults`.
- **Tests split** into `*.UnitTests` (pure) and `*.IntegrationTests` (EF Core against in-memory SQLite via the `SqliteDatabase` helper; biobank API via `WebApplicationFactory`). Use xUnit; no FluentAssertions.
- **Add packages via central management:** `dotnet add <project> package <name>` updates `Directory.Packages.props`. Do not hand-edit versions onto a `PackageReference`.

## What to avoid

- **Do not `git commit`, `git push`, or create branches/PRs without the user's explicit permission.** Make changes in the working tree and let the user review and commit.
- Do not commit secrets or a real `.env`; configuration comes from environment variables.
- Do not bypass the layers (no EF Core / `HttpClient` / `XmlReader` in `Application` or `Domain`).
- Do not put NuGet versions on individual `PackageReference`s - use central package management.
- Do not loosen analyzer/format settings to silence errors; fix the code instead.
- Do not introduce a shared project between the services - keep their domains decoupled.
